## 1. システム概要

### 1.1 目的

春から秋、早朝から夕方にかけて、住宅街および里山地域の田畑・道路脇でツキノワグマを監視・検知し、**猟友会および警察へ通報する**。住民への直接的な即時警報は行わない。

### 1.2 この目的から導かれる最重要制約

通報先が専門機関であるため、**適合率（precision）が再現率より優先する**。誤報を数回送れば運用そのものが停止する。逆に通報までの遅延要件は緩く、数分で足りる。

### 1.3 スコープ外

| 項目 | 理由 |
|---|---|
| 夜間監視 | 端末のIRカットフィルタにより原理的に不可 |
| 全天球・パノラマ合成 | 前後カメラに重複がなく不要 |
| 三角測量による位置特定 | 単一端末のため方位＋推定距離のみ |
| 住民向け即時警報 | 本サービスの目的外 |

### 1.4 処理フロー

```
[端末]
  S1  背景差分            1280×720 グレースケール・2秒間隔
  S2  トラック生成         幾何・時間フィルタで選別
  S3  ROI分類器            96×96 軽量CNN（動物らしさの2値判定）
   |
   +--> 投機的録画開始（サーバ応答を待たない・リングバッファ併用）
   |
   +--> 高解像度静止画＋メタデータをアップロード
[サーバ]
  S4  即時判定            再現率重視。動物／非動物。映像要求を決める
  S5  事後判定            適合率重視。歩容・移動で種を確定
   |
   +--> 人間確認キュー（初年度は必ず経由する）
   |
   +--> 猟友会・警察へ通報
```

## 2. 未決定事項

各項目は後続の設計を分岐させる。段階的に決定し、決定したら「決定済み」に更新する。

| グループ | 決定期限 | 対象 | 理由 |
|---|---|---|---|
| **M1 着手前に必須** | Phase 0 完了後すぐ | D-1, D-5 | サーバ構成と端末更新方針が決まらないと M1/M2 の設計が書けない |
| **Phase 1-Test 前に必須** | Phase 1-Dev 完了まで | D-2, D-4, D-6 | 現地試験には通報経路・確認体制・実施主体の合意が必要 |

### D-1. サーバの設置環境【決定済み】

**決定**: 初期はセルフホスト（開発用 PC）。台数増加時にクラウド移行。

| 項目 | 内容 |
|---|---|
| ハードウェア | AMD Ryzen 7 7735HS / RAM 32GB / AMD Radeon 内蔵GPU（NVIDIA なし） |
| 推論方式 | CPU 推論（torchvision）。Phase 1 は端末 1 台のため十分 |
| 拡大時 | NVIDIA GPU 追加、またはクラウド（GPU インスタンス）へ移行 |

> S4 の `fasterrcnn_resnet50_fpn_v2` は CPU で 1 枚数秒。即時判定としては許容範囲。S5 はバッチ処理で夜間に回す。

### D-2. 通報手段と受け手の体制

| 選択肢 | 備考 |
|---|---|
| メール（SMTP） | 最も確実。既読確認ができない |
| LINE Messaging API | **LINE Notifyは2025年3月末で終了済み。Messaging APIを使うこと** |
| SMS（Twilio等） | 到達性が高い。従量課金 |
| 専用Webページ＋ポーリング | 受け手にアプリを入れさせない |

**決定すべきこと**：手段／宛先の人数／受領確認（ack）の要否／夜間の扱い（時間外は翌朝まとめる等）

### D-3. 開発言語とフレームワーク【決定済み】

| 領域 | 決定 | 制約 |
|---|---|---|
| 端末アプリ | Kotlin / minSdk 24 / targetSdk 34 | Android 7.0〜14。**NNAPIは使えない（API 27以降）** |
| 画像処理 | OpenCV Android SDK | APK肥大（ABI絞りで約40MB）。自前実装なら軽いが工数増 |
| 端末推論 | TFLite 2.4.0 + CPU（XNNPACK 無効） | NNAPI不可。TFLite 2.10+ は Cortex-A53 でネイティブクラッシュ（§3.2） |
| サーバ | Python 3.11 / FastAPI / Uvicorn | |
| DB | SQLite（初期）→ PostgreSQL（台数増時） | |
| サーバ推論 | **torchvision (BSD-3-Clause) + PyTorch** | D-7 の方針により AGPL 系は使わない |
| 確認UI | FastAPI + サーバサイドレンダリング | **確認者がスマホで操作する前提** |

### D-4. Phase 2 の設置箇所数と確認体制

**決定すべきこと**：設置候補地の数／人間確認キューを回す担当者の人数／1日に確認に割ける時間

> 1日50件の確認は、1件10秒でも8分強かかる。担当が1人なら上限は50件/日と考えてよい。

### D-5. 端末アプリの更新手段【決定済み】

**決定**: APK は手動更新（Google Drive 等から端末で DL）。設定パラメータはハートビート応答でリモート配信。

> §11 の設定項目を全てリモート変更可能にすれば、APK 更新が必要になる頻度は低い。APK 更新時は現地訪問または端末でブラウザから DL。

### D-6. 実施主体

個人開発か、自治体・猟友会等との共同か。共同の場合、個人情報の取り扱い、成果物の帰属、通報の責任範囲を先に文書化する必要がある。

### D-7. モデルのライセンス方針【決定済み】

**BSD / Apache-2.0 系のみを使う。AGPL-3.0 のモデル実装は採用しない。**

Ultralytics YOLO は AGPL-3.0 であり、ネットワーク越しにサービスとして提供する場合もソース開示義務が生じる。将来的に自治体や猟友会へ提供する可能性がある以上、最初から避ける。あとから乗り換えると学習パイプラインを作り直すことになる。

| 段 | 採用 | ライセンス |
|---|---|---|
| S3 端末側 ROI 分類器 | torchvision `mobilenet_v3_small` | BSD-3-Clause |
| S4 サーバ即時判定 | torchvision `fasterrcnn_resnet50_fpn_v2` または `retinanet_resnet50_fpn_v2` | BSD-3-Clause |
| S5 映像事後判定 | torchvision バックボーン + 自前の系列分類器 | BSD-3-Clause |

事前学習重みも同じライセンスで配布されている。COCO 事前学習のクラス集合は Ultralytics と同一なので、初年度の「動物クラスの和集合」運用はそのまま成立する。

CPU 推論では `fasterrcnn_resnet50_fpn_v2` が 1 タイルあたり数秒かかるが、S4 は通報遅延の要件が緩い（数分でよい）ため許容できる。速度が問題になったら `ssdlite320_mobilenet_v3_large` を検討するが、小さい対象には弱いので安易に切り替えないこと。

**S3 の端末側配置**は PyTorch で学習し、ONNX 経由または `ai-edge-torch` で TFLite に変換する。Android 7.0 では NNAPI が使えないため XNNPACK の CPU 実行になる。

## 3. 端末素性（Phase 0 で確定させ、判明次第ここに追記する）

対象端末：**HUAWEI MediaPad T3 8 (KOB-L09)** — Snapdragon 425 / RAM 2GB / Android 7.0 (EMUI 5.1)

| 項目 | 期待値 | 実測値 | 影響 |
|---|---|---|---|
| `INFO_SUPPORTED_HARDWARE_LEVEL` | LEGACY と想定 | **LIMITED** | Camera2 API を採用。Camera1 フォールバックは不要 |
| 露出ロック可否 | 可 | **可** | S1 は移動中央値でなくフレーム間差分で成立する |
| フォーカス無限遠固定 | 不明 | **背面: 可（AF_MODE_OFF あり） / 前面: 可（OFF のみ）** | 背面は無限遠固定可能。前面は固定焦点 |
| プレビュー最大解像度 | 1280×720 | **前面 1600×1200 / 背面 2592×1944** | 想定を上回る。検知用は 1280×720 に下げて処理負荷を抑える |
| 静止画最大解像度 | 2592×1944 | **前面 1600×1200 / 背面 2592×1944** | プレビューと同値 |
| 背面カメラ実測水平画角 | 60〜70度 | **74.4°**（センサー 3.63×2.72 mm から算出・要実測） | 角分解能は低下するが監視範囲が広い |
| 前面カメラ実測水平画角 | 55〜65度 | **62.7°**（センサー 2.83×2.13 mm から算出・要実測） | 期待範囲内 |
| ABI | arm64-v8a と想定 | **arm64-v8a, armeabi-v7a, armeabi** | arm64-v8a でビルド。32bit フォールバックも可 |
| 前後交互撮影の所要時間 | 2秒以下 | **765 ms（中央値）** | 余裕あり。min 639 / max 855 ms |
| 背景差分1フレーム所要 | 50ms以下 | **14 ms（中央値）** | 余裕あり。OpenCV 使用時も十分に収まる見込み |
| 96×96 CNN 1推論 | 200ms以下 | **未測定（TFLite 2.14.0 がネイティブクラッシュ）** | TFLite バージョンまたはデリゲートの変更で要再検証 |

### 3.1 端末互換性マトリクス

本システムは minSdk 24（Android 7.0）〜 targetSdk 34（Android 14）の範囲をサポートする。端末を追加するたびに `device_probe` で Go/No-Go を実施し、この表に追記する。

| 項目 | MediaPad T3 8 (API 24) | Xiaomi 12T Pro (API 34) | 備考 |
|---|---|---|---|
| Go/No-Go | #1〜#6 Go / #7〜#9 検証中 | 未実施 | |
| Foreground Service | 型指定不要 | `foregroundServiceType` 必須 | API 34 で必須化 |
| 通知パーミッション | 自動表示 | `POST_NOTIFICATIONS` 必須 | API 33 で必須化 |
| ストレージパーミッション | `WRITE_EXTERNAL_STORAGE` | 不要（Scoped Storage） | API 29 で変更 |
| BroadcastReceiver | フラグ不要 | `RECEIVER_NOT_EXPORTED` 必須 | API 33 で必須化 |
| 正確アラーム | `setExactAndAllowWhileIdle` | `USE_EXACT_ALARM` 必須 | API 31 で変更 |
| Camera Session API | `createCaptureSession(List)` | `SessionConfiguration` | API 28 で非推奨化 |
| TFLite | 2.4.0（2.10+ でクラッシュ） | 未検証 | §3.2 参照 |
| サービス状態確認 | `getRunningServices`（動作） | 空リストを返す場合あり | `isRunning` フラグで統一 |

**端末追加手順：**

1. `device_probe` をインストールし、Camera Probe → Benchmark → Endurance 72h を実行
2. 結果 JSON をこの表に転記し、Go/No-Go を判定
3. API レベル分岐が新たに必要な箇所がないか確認し、必要なら対応してから既存端末でリグレッションテスト

### 3.2 既知の端末固有制約

| 制約 | 影響端末 | 対策 |
|---|---|---|
| TFLite 2.10+ がネイティブクラッシュ | MediaPad T3 8（Cortex-A53 + Android 7.0） | TFLite 2.4.0 固定、XNNPACK 無効 |
| SELinux で `/sys/class/thermal/` アクセス拒否 | MediaPad T3 8 | `BatteryManager.EXTRA_TEMPERATURE` で代替 |

### 3.3 設計分岐（Phase 0 の結果に応じて）

| 結果 | 分岐 | 状況 |
|---|---|---|
| 露出ロック不可 | S1をフレーム間差分から**移動中央値の背景モデル**に変更し、グローバル輝度正規化を必須化する | **解消：AE ロック可** |

| 筐体内温度が室内で45℃超 | 筐体を再設計。屋外投入は保留 | **未検証：筐体内温度テスト待ち** |

## 4. システム構成

```
┌─ 端末（Androidタブレット）× N ───────────────┐
│  CaptureService     カメラ制御・フレーム供給        │
│  DetectionPipeline  S1 背景差分 → S2 トラック → S3 分類 │
│  Recorder           リングバッファ・投機的録画        │
│  UploadQueue        永続キュー・再送・帯域制御        │
│  ConfigManager      リモート設定の取得と適用         │
│  Calibration        方位・接地点距離LUT・マスク       │
│  MetricsCollector   §12の指標を集計して送信          │
└──────────────────────────────────────────┘
                    │ HTTPS
┌─ サーバ ────────────────────────────────┐
│  Ingest API         イベント受信・メディア受信        │
│  S4 Inference       静止画の即時判定                │
│  S5 Inference       映像の事後判定（バッチ）          │
│  PrivacyMasker      人物・車両の自動マスク           │
│  ReviewQueue        人間確認キュー（Web UI）         │
│  Notifier           通報（D-2で決定した手段）         │
│  DeviceRegistry     設定配信・死活監視              │
│  DatasetExporter    COCO / YOLO 形式で書き出し       │
└──────────────────────────────────────────┘
```

## 5. 機能要件

### 5.1 端末

| ID | 要件 |
|---|---|
| FR-D01 | 起動時および電源復帰時に自動で監視を開始する |
| FR-D02 | 設定された監視時間帯（既定 05:00〜19:00）のみ稼働し、時間外はスリープする |
| FR-D03 | 前面・背面カメラを**交互に**使用する（同時使用は行わない） |
| FR-D04 | プレビューフレームを既定2秒間隔で取得し、背景差分にかける |
| FR-D05 | 検出した前景領域をフレーム間で対応付け、トラックを生成する |
| FR-D06 | トラックに対し、見かけサイズ・移動速度・持続フレーム数・マスク領域による選別を行う |
| FR-D07 | 選別を通過したROIを96×96に正規化し、軽量CNNで動物らしさを判定する |
| FR-D08 | S3が閾値を超えた時点で、**サーバ応答を待たず**録画を開始する |
| FR-D09 | 直近N秒（既定15秒）のフレームをリングバッファに保持し、録画開始時に前置する |
| FR-D10 | 高解像度静止画とメタデータをアップロードキューに投入する |
| FR-D11 | サーバから映像要求を受けたら、該当録画をアップロードする |
| FR-D12 | サーバが不通の場合、イベントをローカルに永続化し、復旧後に再送する |
| FR-D13 | 日次の通信量上限（既定10MB）に達したら送信を停止し、以降はローカル保存のみとする |
| FR-D14 | 定期的にハートビートを送信し、応答として設定とコマンドを受け取る |
| FR-D15 | 筐体内温度が閾値（既定55℃）を超えたら、**監視を停止して端末を保護する** |
| FR-D16 | ストレージ残量が閾値を下回ったら、古い録画から自動削除する |
| FR-D17 | §12の運用指標を集計し、ハートビートに添えて送信する |
| FR-D18 | サーバコマンドで**試験モード**を起動できる（§9.5） |
| FR-D19 | 試験モードは時間およびストレージの上限で**必ず自動終了する** |

### 5.2 サーバ

| ID | 要件 |
|---|---|
| FR-S01 | イベントとメディアを受信し、永続化する |
| FR-S02 | 受信した静止画に対しS4推論を行い、動物／非動物を判定する |
| FR-S03 | S4が動物と判定した場合、該当端末に映像アップロードを要求する |
| FR-S04 | 受信した映像に対しS5推論をバッチで行い、種を推定する |
| FR-S05 | **人間確認キューに投入する前に、人物・車両を自動マスクする** |
| FR-S06 | 人間確認キューのWeb UIを提供する（スマホで操作可能なこと） |
| FR-S07 | 人がクマと判定したイベントについて通報を送出する |
| FR-S08 | 同一個体と推定される複数端末・短時間の検知を統合し、**通報を重複させない** |
| FR-S09 | 端末の設定を配信し、遠隔から変更できる |
| FR-S10 | 端末のハートビート途絶を検出し、管理者に通知する |
| FR-S11 | 蓄積データをCOCO形式およびYOLO形式で書き出す |
| FR-S12 | §12の運用指標を集計し、ダッシュボードで表示する |

## 7. データモデル

### 7.1 Event

イベントの状態遷移。

```
DETECTED → RECORDING → PENDING_UPLOAD → UPLOADED
                                          ↓
                          SERVER_REJECTED / MEDIA_REQUESTED
                                                ↓
                                          MEDIA_UPLOADED → REVIEWED
```

```jsonc
{
  "event_id": "uuid",              // 端末が採番。冪等性キーを兼ねる
  "device_id": "string",
  "detected_at": "ISO8601 UTC",    // 端末時刻
  "clock_offset_ms": 0,            // NTPとの差。必ず記録する
  "camera": "front | rear",
  "location": { "lat": 0.0, "lon": 0.0 },

  "roi": { "x": 0, "y": 0, "w": 0, "h": 0 },   // プレビュー座標系
  "azimuth_deg": 0.0,              // 校正済みの真方位
  "elevation_deg": 0.0,
  "estimated_distance_m": 0.0,     // 接地点LUTによる推定
  "estimated_size_m": 0.0,

  "track": {
    "duration_s": 0.0,
    "frames": 0,
    "speed_mps": 0.0,
    "direction_deg": 0.0,
    "straightness": 0.0            // 0-1。直線的な移動ほど1に近い
  },

  "env": {
    "weather": "string | null",
    "mean_luminance": 0,
    "global_luminance_delta": 0,   // 直前フレームからの全体輝度変化
    "enclosure_temp_c": 0.0
  },

  "scores": { "s3": 0.0, "s4": null, "s5": null },
  "media": { "still_path": null, "video_path": null },

  "review": {
    "label": null,                 // §7.2 のクラス
    "fp_cause": null,              // §7.3 の原因コード
    "reviewer_id": null,
    "reviewed_at": null
  },
  "notified_at": null
}
```

### 7.4 校正データ（端末ごと・1ファイル）

```jsonc
{
  "device_id": "string",
  "installed_at": "ISO8601",
  "mast_height_m": 3.0,
  "cameras": {
    "rear": {
      "hfov_deg": 65.0,            // Phase 0 の実測値
      "focal_px": 0.0,
      "azimuth_offset_deg": 0.0,   // 設置時にランドマークを視準して決定
      "pitch_deg": -5.0,
      "roll_deg": 0.0,
      "ground_lut": [              // 接地点の画素行 → 距離
        { "azimuth_bin_deg": 0, "rows": [[100, 8.0], [200, 15.0], [400, 52.0]] }
      ],
      "masks": [                   // 除外する多角形（プレビュー座標系）

}
```

> `ground_lut` は現地でレーザー測距計を使い、方位10度刻み・距離10m刻みの実測点から作る。作成を支援するツール（`tools/calibrate_ground.py`）を用意すること。平坦地の仮定は斜面で簡単に破綻する。

> **校正ファイルは Git 管理外とする。** 設置地点の座標を含むため。`.gitignore` で `calib/` `*_calib.json` `site_*.json` を除外済み。サーバ側で端末ごとに保管し、必要なら暗号化バックアップを別途取る。

## 8. API 仕様

すべて HTTPS。認証は端末ごとの Bearer トークン。

> Android 7.0 のルート証明書ストアは古く、Let's Encrypt の新しいルート証明書を持たない。**`network_security_config` に自前CAを同梱すること。**

| メソッド | パス | 用途 |
|---|---|---|
| `POST` | `/v1/events` | イベント＋縮小画像（multipart）。`event_id` で冪等 |
| `POST` | `/v1/events/{id}/still` | 高解像度静止画 |
| `POST` | `/v1/events/{id}/video` | 映像 |
| `POST` | `/v1/heartbeat` | 死活＋指標送信。応答で設定とコマンドを受け取る |
| `GET` | `/v1/config` | 現在の設定（ETag対応） |

### 8.1 ハートビート応答

```jsonc
{
  "server_time": "ISO8601 UTC",     // 端末はこれで時刻ドリフトを補正する
  "config_etag": "string",
  "config": { },                     // 変更があれば同梱（§11）
  "commands": [
    { "type": "request_video", "event_id": "uuid" },
    { "type": "discard", "event_id": "uuid" },
    { "type": "capture_now" },       // 現地確認用
    { "type": "reboot" }
  ]
}
```

**コマンドはポーリング方式とする。** 端末に到達可能なIPがない前提のため、サーバからのプッシュは想定しない。ハートビート間隔（既定60秒）が映像要求の遅延の上限になる。

## 9. 端末アプリの設計

### 9.1 検知パイプラインの詳細

**S1 背景差分**

- 入力：プレビューフレーム（1280×720 想定）をグレースケール化
- 背景モデル：移動中央値、または OpenCV `BackgroundSubtractorMOG2`
- **グローバル輝度補正を先に行う**：フレーム全体の平均輝度が閾値以上変化した場合、そのフレームは破棄する（雲の通過・露出変動対策）
- 出力：前景マスク → 連結成分 → 候補ROI

**S2 トラック生成とフィルタ**

以下をすべて満たすトラックのみ通す。すべて計算コストはほぼゼロで、誤検知削減の効果が最も大きい部分。

| フィルタ | 内容 |
|---|---|
| 接地点サイズ | ROI下端のy座標から `ground_lut` で距離を引き、期待される見かけサイズの範囲外を除外 |
| アスペクト比 | 極端に細長い／平たいものを除外 |
| 持続 | 3フレーム以上連続して追跡できたもののみ |
| 速度 | 0.3〜3.0 m/s 相当（走行時は別枠で6 m/s まで） |
| 直進性 | 往復運動（草の揺れ）を除外 |
| マスク | `masks` に含まれる領域を除外 |

**S3 ROI分類器**

- MobileNetV3-Small 相当、入力96×96、出力2クラス（動物らしい／ノイズ）
- 初期は学習データがないため、**閾値を極端に低くして事実上素通しにする**。Phase 2 のデータが貯まってから本格運用する
- Phase 2 開始時点でモデルがなくても動くよう、バイパス可能に実装すること

### 9.2 録画

- リングバッファに直近15秒のフレームを保持
- S3通過時点で録画開始。バッファ内容を前置する
- 形式：MP4 / H.264 / 640×480 / 15fps（`MediaRecorder` のハードウェアエンコーダを使用）
- 最大録画長：既定30秒
- **サーバ応答を待たない。** 不要と判定されたら削除する

### 9.3 アップロードキュー

- SQLite による永続キュー。プロセス再起動・電源断で失われないこと
- 送信順序：新しいものを優先（古い未送信が新しい検知を遅らせないため）
- 指数バックオフでリトライ
- 日次通信量カウンタを持ち、上限到達で送信停止（ローカル保存は継続）

### 9.5 試験モード

Phase 1-Test の距離別試験を実施するために必須の機能。通常運用では S1 が落とした候補は記録が残らないため、「検知しなかった」ことしか分からず、なぜ落ちたのかを追えない。

サーバから `{"type":"test_mode","mode":"stage_trace","duration_s":900}` を送って起動する。

| モード | 記録内容 | 用途 |
|---|---|---|
| `raw_all` | 全プレビューフレームを無条件保存（S1以降をバイパス） | 素材の収集、`replay.py` での再現 |
| `stage_trace` | 通常のパイプラインを回しつつ、各候補について**どの段のどのフィルタで落ちたか**を1件ずつ記録 | **Phase 1-Test の本命。** 検知率が出ない原因の特定 |

`stage_trace` が記録する内容。

```jsonc
{
  "frame_ts": "ISO8601 UTC",
  "candidates": [
    { "roi": {"x":0,"y":0,"w":0,"h":0},
      "stage_reached": "S2",
      "rejected_by": "size_from_ground",   // null なら通過
      "detail": {"expected_h_px": 22.4, "actual_h_px": 61.0},
      "track_id": 17, "track_frames": 4, "speed_mps": 0.9 }
  ],
  "global": { "luminance": 128, "luminance_delta": 3, "fg_pixels": 412 }
}
```

棄却理由のコード：`global_luminance` / `size_from_ground` / `aspect_ratio` / `min_track_frames` / `speed_range` / `straightness` / `mask_region` / `s3_threshold`

安全上の要件。

- **時間上限（`test_mode.max_duration_s`、既定900秒）とストレージ上限（`test_mode.max_storage_mb`、既定4096MB）で必ず自動終了する。** 両者は hard clamp 対象であり、設定ミスで走りっぱなしにできない
- 記録はアップロードしない。容量が大きいため現地回収または Wi-Fi 圏内でまとめて送る
- 通知バーに「試験モード動作中」を常時表示し、放置に気づけるようにする
- 通常の日次通信量上限とは別枠で管理する

### 9.4 常駐と復帰

- Foreground Service + `PARTIAL_WAKE_LOCK`
- `BOOT_COMPLETED` レシーバで自動起動
- **EMUI の「保護されたアプリ」「起動管理」への登録手順を README に明記すること。** ここを忘れると EMUI がアプリを終了させる
- ウォッチドッグ：`AlarmManager` で定期的に自己監視し、パイプラインが停止していたら再起動

## 10. サーバの設計

### 10.1 プライバシーマスク（FR-S05）

人間確認キューに出す前に、YOLOで `person` と車両クラスを検出し、該当領域をぼかす。確認者が見るのは常にマスク済みの画像とする。

**元画像はマスクなしで保存するが、アクセス権限を分離する。** 学習用途では人物領域を含む元画像が必要になるため。

### 10.2 通報の重複抑制（FR-S08）

以下をすべて満たす複数イベントは、同一個体として1件に統合する。

- 検知時刻が既定300秒以内
- 推定位置が既定200m以内（各端末の方位＋推定距離から算出）

### 10.3 人間確認キューのUI要件

- 1件あたり10秒以内で処理できること
- 画面構成：静止画１枚＋短い動画＋ラベルのワンタップ選択＋誤検知時の原因選択
- **スマホで操作できること**（確認者は移動中に処理する）
- 未処理件数と滞留時間を常に表示する

### 10.5 モデルの選定

D-7 の方針により **torchvision（BSD-3-Clause）のみ**を使う。Ultralytics YOLO は AGPL-3.0 のため採用しない。

| 段 | モデル | 備考 |
|---|---|---|
| S4 | `fasterrcnn_resnet50_fpn_v2` | 小さい対象に強い。CPU で1タイル数秒だが遅延要件が緩いので可 |
| S4（軽量代替） | `retinanet_resnet50_fpn_v2` | 速度が問題になった場合 |
| S5 | torchvision バックボーン + 自前の系列分類器 | 速度プロファイル・サイズ変化・アスペクト比変化を特徴量にする |

高解像度静止画はタイル分割して推論し、重複領域は NMS で統合する。

### 10.4 データセット書き出し（FR-S11）

- COCO形式（検出用）と YOLO txt 形式（学習用）の両方
- **分割は時系列と地点で行う。** ランダム分割は同一個体の連続フレームが学習側と評価側に混ざり、性能を過大評価する
  - 学習：Phase 2 前半 かつ 地点A・B
  - 検証：Phase 2 後半 かつ 地点A・B
  - 評価：地点C（学習に一切使わない地点）

## 13. セキュリティとプライバシー

| 項目 | 方針 |
|---|---|
| 端末認証 | 端末ごとのBearerトークン。失効可能にする |
| 通信 | HTTPS。Android 7.0 対策として自前CAを `network_security_config` に同梱 |
| 保存 | 元画像はマスクなしで保存。**アクセス権限を確認者用と学習用で分離する** |
| 確認者が見る画像 | 常に人物・車両をマスク済みのもの |
| 保存期間 | 誤検知は30日、動物検知は無期限（学習用）、人物が写ったものは目的達成後速やかに削除 |
| 掲示 | 設置場所に撮影中である旨・目的・問い合わせ先を掲示 |
| 準拠 | 個人情報保護委員会「カメラ画像利活用ガイドブック」 |
| 端末の盗難・破損 | 施錠固定。盗難時はトークンを失効。端末内に個人情報を長期保持しない |
| **Git 管理** | **撮影データ（画像・映像・イベント）と、座標を含む校正ファイルは絶対にコミットしない。** 通行人が写り込む以上、リポジトリに個人情報を入れることになる。`.gitignore` で除外済み。コミット前に必ず `git status` を確認する |

### 実装上の重要な指針

- **M0.5（開発基盤）を M1 より前に完了すること。** `fake_device.py` がないとサーバ開発のたびに実機が必要になり、`replay.py` がないと閾値調整のたびに現地に行くことになる。これらは機能ではなく開発速度を決めるインフラである
- **端末を追加したら §3.1 の互換性マトリクスを更新し、全テストを回すこと。** API レベル分岐の漏れは実機でしか発覚しない
- S3 は最初からバイパス可能に実装する（モデルがない期間が長い）
- 設定は全てリモート変更可能に（§11）
- メトリクスは機能実装と同時に入れる（後付けは必ず漏れる）

## 15. テスト戦略

| レベル | 対象 | 方法 | 自動化 |
|---|---|---|---|
| 単体 | フィルタ、LUT補間、方位変換、設定検証 | pytest（サーバ）/ Google Test 相当（端末） | CI で PR ごとに実行 |
| 再現 | 検知パイプライン全体 | 録画済み映像を `replay.py` に通し、期待される検知数と比較 | CI で回帰テストセット実行 |
| 統合 | 端末⇔サーバ | `fake_device.py` で API を叩く | CI で実行 |
| 障害 | キュー・復帰 | §16 Phase 3 の障害試験を自動化 | 手動（環境構築が必要） |
| 実地 | 検知率 | §16 Phase 1-Test の距離別試験 | 手動（現地実施） |
| 端末互換性 | 全対応端末での基本動作 | `device_probe` の全テスト実行 | 手動（実機が必要） |

### 15.1 CI（継続的インテグレーション）

M0.5 で GitHub Actions を設定する。以下を PR ごとに自動実行する。

- `pytest tests/` — 設定検証・ロールバック・サーバロジックの単体テスト
- `replay.py` による回帰テスト（Phase 1-Test 以降、正解つきテストセットが揃ってから）
- `fake_device.py` による E2E 疎通（M1 以降）

**Android 側は CI での自動ビルドを M2 以降で検討する。** 端末互換性テストは実機依存のため手動だが、結果 JSON を構造化して `testlogs/` に保存し、端末間の比較を可能にする。

**回帰テスト用に、Phase 1-Test で撮影した映像を「正解つきテストセット」として保存すること。** 閾値やモデルを変えるたびに、これを流して劣化していないか確認する。

### Phase 0：机上・室内検証

- 自前 CA での TLS 疎通
- 想定筐体での室内 72 時間・温度記録

**Go 判定**：露出ロック可、プレビュー 1280×720 可、72 時間常駐成功、室温下で筐体内 40℃以下
**No-Go**：常駐できない、プレビューが 640×480 止まり → 端末変更

### Phase 1-Test：単機・既知条件の距離別試験

**Entry Criteria**: Phase 1-Dev の Exit Criteria を満たしていること。D-2（通報手段）・D-4（確認体制）・D-6（実施主体）が決定済みであること

繰り返し立ち入れる開けた場所に、端末から 10 / 20 / 30 / 50 / 70 m の距離マーカーを設置する。

**標的**：高さ 1.0m × 幅 1.4m の板に濃茶〜黒の布を張り、台車で引く。サイズと色の両方がクマに近く、距離をそのまま解釈できる。人を代役にする場合は身長 1.7m を **1.7 倍の距離**に立たせる（クマ 50m ≒ 人 85m）。

**条件**：距離 × 時間帯（早朝／日中／夕方）を主軸に、速度（歩行／走行／静止）、天候、逆光、遮蔽を可能な範囲で網羅。各セル最低 3 回。

**試験は `stage_trace` モード（§9.5）で行う。** 通常運用では S1 が落とした候補の記録が残らず、「検知しなかった」ことしか分からない。棄却理由まで記録して初めて、検知率が出ない原因（サイズフィルタが厳しすぎる／輝度変動で破棄されている／マスクに掛かっている）を特定できる。記録は現地回収し、`tools/replay.py` で閾値を変えながら再実行する。

| 指標 | 合格基準 |
|---|---|
| 検知率 @30m | ≥ 95% |
| 検知率 @50m | ≥ 80% |
| 検知率 @50m 逆光時 | ≥ 50%（低下量の把握が目的） |
| 誤検知件数 | ≤ 50 件/日 |
| 通信量 | ≤ 10 MB/日 |
| 端末稼働率 | ≥ 98% |
| 筐体内最高温度 | ≤ 45℃ |
| 電池収支 | 24 時間で成立 |
| 端末→サーバ受信遅延 | 中央値 ≤ 30 秒 |
| 録画の取りこぼし | ≤ 10% |

**Go 判定**：上記を満たす。**判定者は D-6 で決定した実施主体**。自治体・猟友会との共同の場合、Go 判定に合意を要する
**設計変更**：検知率 @50m 未達 → 監視距離を 30m に縮小して仕様を見直す。**仕様変更はステークホルダーの合意を経ること**
**No-Go**：温度 55℃超、または電池収支不成立 → 筐体・電源から再設計

### Phase 2：実地・単機

**設置前**：土地所有者の同意（書面）、自治体との協議、猟友会への説明と通報経路の合意、掲示、運用ルール文書化、画角確認（住宅の窓・玄関が入らないこと）、**方位別見通し距離の実測（10度刻み）**

**設置条件**：カメラは**北向きを原則**（早朝・夕方の逆光回避）。地上2.5〜3.5m。設置時にランドマークを視準して方位を校正。

**運用方針**：S5の自動判別は初年度に成立しない。S4は汎用の動物検出で運用し、通過したものは全て人間確認キューに流す。**人がクマと判定したもののみ通報する。**

| 指標 | 目標 |
|---|---|
| 確認キューの日次件数 | ≤ 50 件/日 |
| 各クラスの蓄積枚数 | 主要クラスで ≥ 500 枚 |
| ツキノワグマの蓄積枚数 | ≥ 100 枚 |
| 方位別の実効見通し距離 | 全方位で実測完了 |
| 通信費 | ≤ 1,000 円/月/台 |
| 累積稼働率 | ≥ 95% |
| 苦情件数 | 0 件 |

### Phase 3：複数台・サーバ負荷

端末4〜6台。意図的な障害試験を行う。

- サーバ30分停止 → 再送成功率 100%
- 端末電源10分遮断 → 自動復帰 ≥ 95%
- LTE圏外30分 → キュー蓄積と再送
- 全端末同時イベント → 処理遅延 ≤ 60秒
- ストレージ満杯 → 自動削除の動作

### Phase 4：モデル学習と評価

分割は§10.4の通り、時系列と地点で行う。

| 指標 | 合格基準 | 根拠 |
|---|---|---|
| S3 再現率 | ≥ 95% | 端末で落とすと回復不能 |
| S4 再現率（動物） | ≥ 95% | 同上 |
| S4 適合率（動物） | ≥ 50% | 通信量を絞れれば足りる |
| **S5 適合率（クマ）** | **≥ 95%** | **誤報が信頼を壊す** |
| S5 再現率（クマ） | ≥ 70% | 見逃しは他手段で補える |
| 誤報頻度 | ≤ 1 件/週/システム全体 | 運用継続の下限 |

**S5の適合率が95%に届かない場合、自動通報は行わず人間確認キューを継続する。** これは想定内の分岐であり、失敗ではない。

## 17. リスクと中止基準

| リスク | 予兆 | 対応 | 中止基準 |
|---|---|---|---|
| 電池の熱暴走・発火 | 筐体内50℃超、電池膨張 | 温度による自動停止（FR-D15） | 筐体内60℃到達で即時停止 |
| 通信費の暴走 | 日次通信量が上限超過 | 日次上限で送信停止（FR-D13） | 月額3,000円/台超で見直し |
| 誤検知過多 | 確認キューが100件/日超 | S2フィルタを締める、マスク追加 | 200件/日超が1週間継続 |
| プライバシー苦情 | 苦情1件目 | 即座に画角・掲示を見直し記録 | 苦情2件目で当該地点を撤去 |
| 学習データ不足 | クマの蓄積が50枚未満 | 他地域データとの併用を検討 | Phase 4を1年延期 |
| 端末の入手性 | 中古市場からの消失 | 代替機種を事前に2機種選定 | — |
| サーバの単一障害 | ハートビート途絶 | 端末側キューで吸収 | — |

**温度による自動停止（FR-D15）は必ず実装すること。** 住宅街や田畑にリチウム電池入りの機器を無人で置く以上、任意ではなく安全上の必須要件である。中古端末は電池が既に劣化している個体も多く、新品より高温耐性が低いと考えること。
