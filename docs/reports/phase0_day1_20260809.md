**日付**: 2026-08-09

## Step 0: Camera Probe（カメラ素性の取得）

### 初期仮説

SPEC.md §3 の未決定事項として、端末の HW Level が LEGACY の可能性があり、その場合 Camera2 API が使えず Camera1 API へのフォールバックが必要になる。また、AE ロックの可否が S1（背景差分）の成立条件であり、不可であれば設計の根本変更が生じる。

### 方法

`tools/device_probe` アプリの **[Camera Probe]** ボタンを実行。Camera2 API の `CameraCharacteristics` から HW Level、AE ロック、AF モード、解像度、センサーサイズ、推定画角を取得した。

### 結果

| 項目 | Camera 0（背面） | Camera 1（前面） |
|---|---|---|
| HW Level | LIMITED | LIMITED |
| AE ロック | true | true |
| AF モード | AUTO, OFF, MACRO, CONTINUOUS_VIDEO, CONTINUOUS_PICTURE | OFF |
| 無限遠固定 | 可（AF_MODE_OFF あり） | 可（AF_MODE_OFF のみ） |
| プレビュー最大 | 2592×1944 | 1600×1200 |
| 静止画最大 | 2592×1944 | 1600×1200 |
| 推定 HFOV | 74.4°（要実測） | 62.7°（要実測） |
| センサーサイズ | 3.63×2.72 mm | 2.83×2.13 mm |
| ABI | arm64-v8a, armeabi-v7a, armeabi | （共通） |

### 判定

- **HW Level ≠ LEGACY → Go.** Camera2 API で開発する。Camera1 フォールバックは不要。
- **AE ロック可 → Go.** S1 のフレーム間差分が成立する。
- **プレビュー ≥ 1280×720 → Go.** 検知用解像度は 1280×720 に下げて運用可能。
- **arm64-v8a あり → Go.** ネイティブライブラリは arm64 のみビルドすればよい。

## Step 1: Benchmark（性能計測）

### 初期仮説

Snapdragon 425 (Cortex-A53, 4コア 1.4GHz) は低性能 SoC であり、背景差分・カメラ切替・TFLite 推論のいずれかがボトルネックになる可能性がある。特に RAM 2GB の制約から、カメラ HAL と TFLite を同時に動かすと LMK（Low Memory Killer）に殺されるリスクがある。

### 方法

`tools/device_probe` アプリの **[Benchmark]** ボタンを実行。以下 3 項目を順次計測した。各テストは独立して実行し、TFLite 実行前に GC + 1秒待機を挟んでメモリを解放する設計。

| 計測項目 | 試行回数 | 合格基準 |
|---|---|---|
| 背景差分 1280×720（絶対値差分 + 閾値） | 100 回 | 中央値 ≤ 50 ms |
| 前後カメラ交互切替（open → 1stフレーム → close） | 10 往復 | 中央値 ≤ 2000 ms |
| TFLite 96×96 ダミーモデル推論 | 50 回 | 中央値 ≤ 200 ms |

### トラブルシューティング: TFLite ネイティブクラッシュ

TFLite 推論でアプリがネイティブクラッシュし、3段階の切り分けを行った。

| 試行 | TFLite バージョン | XNNPACK | 結果 |
|---|---|---|---|
| 1回目 | 2.14.0 | デフォルト（有効） | **クラッシュ** |
| 2回目 | 2.10.0 | `setUseXNNPACK(false)` | **クラッシュ** |
| 3回目 | **2.4.0** | `setUseXNNPACK(false)` | **成功** |

**原因**: TFLite 2.10.0 以降の NDK ビルドが Cortex-A53 + Android 7.0 の linker / SIMD 命令セットと非互換。ネイティブ `.so` のロード時点でクラッシュするため、Java の `try-catch` では捕捉不可。

**対策**: `build.gradle.kts` で `org.tensorflow:tensorflow-lite:2.4.0` を使用し、`Interpreter.Options` で `setUseXNNPACK(false)` を明示的に指定する。

**補足**: ビルド時に Kotlin Daemon のメモリ不足エラーも発生。`gradle.properties` に `kotlin.daemon.jvmargs=-Xmx512m` を追加し、Android Studio の Build メニューから直接ビルドすることで解決。

## Step 5: 72h 常駐耐久テスト — Go

### 初期仮説

EMUI はバッテリー最適化のため、画面ロック後にバックグラウンドアプリを積極的にキルする。Foreground Service + WakeLock だけでは不十分な可能性がある。

### 方法

`device_probe` アプリの **[Endurance 72h]** ボタンを押し、1 分間隔でタイムスタンプ・バッテリー残量・温度を JSONL に記録する。**充電器は未接続**（バッテリー運用での減少率を把握するため）。

### トラブルシューティング

#### 問題 1: EMUI によるアプリキル

初回テストでは画面ロック直後にアプリがキルされた。

**対策**: `AndroidManifest.xml` に `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` パーミッションを追加し、`MainActivity` 起動時にシステムダイアログで除外をリクエストするようにした。また `foregroundServiceType="camera"`（API 29+ 属性）を削除。アプリ情報 → 電池 → 「画面ロック時に閉じる」を OFF に設定。

**結果**: キルされなくなった。

#### 問題 2: Doze によるログ間隔の拡大

14.4h テストで、最初の 7h は正確に 1 分間隔だったが、Doze に入った後 11〜40 分に拡大した。`Handler.postDelayed()` が Doze 中に遅延されるため。

**対策**: `AlarmManager.setExactAndAllowWhileIdle()` に変更。

**結果**: 約 5 分間隔で安定（OS のレート制限により 1 分間隔は不可）。耐久テストの目的には十分。

#### 問題 3: CPU 温度が全エントリ 125°C

`/sys/class/thermal/thermal_zone*/temp` が SELinux により `untrusted_app` からアクセス拒否され、TSENS のデフォルト値 125（クリティカルトリップポイント）が返されていた。

**対策**: `BatteryManager.EXTRA_TEMPERATURE`（バッテリー温度、1/10°C 単位）に変更。フィールド名を `cpu_temp_c` → `battery_temp_c` に変更。

**結果**: 26〜28°C の妥当な値が記録されるようになった。

### 最終結果（S6 セッション: 83.2h 連続稼働、無充電）

| 項目 | 値 |
|---|---|
| 稼働時間 | 83.2 時間（72h 合格基準を超過） |
| エントリ数 | 1,005 件 |
| バッテリー残量 | 83% → 69%（14% 消費） |
| 消費レート | **0.168%/h** |
| バッテリー温度 | 24〜33°C（合格基準 45°C 以内） |
| Doze 間隔 | 996/1,005 件（99.1%）が約 300 秒で安定 |
| 途切れ | なし |
| 意図しない停止 | なし |

**バッテリー寿命推定**: 100% → 0% で約 595 時間（約 25 日）。充電器なしでも十分な余裕。

### 判定: **Go**

## Step 6: 電源断からの自動復帰テスト — Go

### 方法

耐久テスト実行中に電源ボタン長押しで強制再起動を実施。`BOOT_COMPLETED` BroadcastReceiver（`BootReceiver.kt`）がサービスを自動再開するか確認する。

### 実装

`BootReceiver.kt` を新規実装し、`AndroidManifest.xml` に `BOOT_COMPLETED` レシーバーを登録。

### 結果

| 端末 | 強制再起動後の自動復帰 | 遅延 | 判定 |
|---|---|---|---|
| **MediaPad T3 8** (EMUI 5.1.3 / API 24) | **成功** | 即時 | **Go** |
| **Xiaomi 12T Pro** (MIUI / API 34) | **成功** | 3〜5 分 | **Go** |

### Xiaomi 12T Pro の起動遅延について

MIUI はブート後のアプリ起動をバッチ処理するため、BOOT_COMPLETED の配信が 3〜5 分遅延する。これは MIUI の標準的な動作であり、監視用途では問題にならない（端末再起動自体が稀なイベント）。

### 判定: **Go**
