# Phase 0 検証マニュアル

device_probe のカメラ素性調査で以下が確定した。本マニュアルは残りの検証手順を記載する。

## 確定済みの素性

| 項目 | 結果 | 設計への影響 |
|---|---|---|
| HW Level | LIMITED | Camera2 API で開発する。Camera1 フォールバックは不要 |
| AE ロック | 可 | S1 はフレーム間差分で成立する |
| プレビュー最大解像度 | 前面 1600×1200 / 背面 2592×1944 | 検知用は 1280×720 に下げて処理負荷を抑える |
| HFOV | 前面 62.7° / 背面 74.4° | 背面の角分解能: 74.4° / 1280px = 0.058°/px |

---

## 残りの検証項目と手順

### Step 1: ベンチマーク計測

device_probe アプリの **[Benchmark]** ボタンを押す。以下 3 項目が自動計測される。

| 計測項目 | 合格基準 | 結果欄 |
|---|---|---|
| 前後カメラ交互切替（10 往復の中央値） | ≤ 2000 ms | |
| 背景差分 1280×720（100 回の中央値） | ≤ 50 ms | |
| TFLite 96×96 推論（100 回の中央値） | ≤ 200 ms | |

**手順：**

1. 他のアプリを全て閉じ、端末を再起動する
2. device_probe を起動し、**[Benchmark]** を押す
3. 3〜5 分待つ（カメラ切替 → 差分 → TFLite の順に実行される）
4. 結果が画面に表示される。各項目の Pass/Fail を確認する
5. **[Export JSON]** で結果を保存する

**TFLite の注意：** ダミーモデル（単層）での計測であり、実際の MobileNetV3-Small はこれより遅い。目安として、ダミーが 50 ms 以下なら実モデルでも 200 ms 以内に収まる見込み。

### Step 2: ABI の確認

Camera Probe の結果 JSON に `device.abis` として記録されている。

**[Export JSON]** で出力したファイルを開き、以下を確認する。

```
"abis": ["arm64-v8a", ...]
```

`arm64-v8a` が含まれていれば OK。OpenCV・TFLite のネイティブライブラリは arm64-v8a のみビルドすればよい。

### Step 3: フォーカス無限遠固定の確認

Camera Probe の結果 JSON に `infinity_focus_possible` と `af_modes` が記録されている。

- `infinity_focus_possible: true`（`AF_MODE_OFF` がある）→ 無限遠固定が可能
- `infinity_focus_possible: false` → AF は常時動作。設置時に近景（柵・ポールなど）がカメラ近傍に入らないよう注意する

### Step 4: 静止画最大解像度の確認

Camera Probe の結果 JSON に `still_max` として記録されている。

背面カメラのプレビュー最大が 2592×1944 なので、JPEG 出力もおそらく同値。確認して SPEC.md §3 の表を埋める。

### Step 5: 72 時間常駐耐久テスト

**目的：** EMUI がアプリを殺さずに 72 時間動作し続けるか確認する。

**事前準備（重要）：**

1. **充電器を接続する**（72 時間はバッテリーだけでは持たない）
2. EMUI の以下を設定する
   - 設定 → アプリ → 詳細設定 → バッテリー最適化の無視 → device_probe を許可
   - 設定 → アプリ → 起動管理 → device_probe を「手動管理」に変更し、3 つのトグル全てを ON
   - ※ EMUI バージョンによりメニュー名が異なる場合がある。「保護されたアプリ」があればそれも ON
3. 画面の自動ロックを 30 分に設定する（テスト中は画面が消えた状態での動作を確認する）

**手順：**

1. 端末を再起動する
2. device_probe を起動し、**[Endurance 72h]** を押す
3. 通知バーに「耐久テスト実行中」が表示されることを確認する
4. 端末を放置する（室温環境、直射日光を避ける）
5. 12 時間ごとに通知バーの表示を確認する（経過時間とバッテリー%）
6. 72 時間後、**[Stop Endurance]** を押す

**結果の確認：**

ログファイル `endurance_log.jsonl` を PC に取り出す。

```bash
adb pull /storage/emulated/0/Android/data/com.bearwatch.probe/files/endurance_log.jsonl
```

以下を確認する。

| 確認項目 | 合格基準 | 確認方法 |
|---|---|---|
| 記録エントリ数 | ≥ 860（= 72h × 12 件/h）※ `setExactAndAllowWhileIdle` の OS レート制限により約 5 分間隔 | `wc -l endurance_log.jsonl` |
| 途切れがないか | 連続する 2 エントリの間隔が 10 分以内 | タイムスタンプの差分を確認 |
| バッテリー温度 | 最大 ≤ 45°C | `battery_temp_c` の最大値（SELinux により CPU 温度は取得不可。バッテリー温度で代替） |
| バッテリー残量 | 充電中なら安定 / バッテリー運用なら減少率の把握 | `battery_pct` の推移 |
| `event: stopped` | 意図しない停止がないか | `grep stopped` で自然停止が混ざっていないか |

**ログ解析の簡易スクリプト：**

```python
import json

entries = [json.loads(l) for l in open("endurance_log.jsonl")]
print(f"エントリ数: {len(entries)}")
print(f"開始: {entries[0]['timestamp_utc']}")
print(f"終了: {entries[-1]['timestamp_utc']}")
temps = [e['battery_temp_c'] for e in entries if e.get('battery_temp_c', -1) > 0]
if temps:
    print(f"バッテリー温度: min={min(temps):.1f}  max={max(temps):.1f}  avg={sum(temps)/len(temps):.1f}")
stops = [e for e in entries if 'event' in e]
print(f"停止イベント: {len(stops)} 件")
```

### Step 6: 電源断からの自動復帰テスト

**目的：** 電源断→復帰で Foreground Service が自動的に再起動するか確認する。

**手順：**

1. 耐久テスト実行中に USB ケーブルを抜き、電源ボタン長押しで強制終了する
2. ケーブルを差し直し、端末が起動するのを待つ
3. 以下を確認する

| 確認項目 | 合格基準 |
|---|---|
| 端末が自動的に起動する | 充電器接続で自動起動する、または手動起動後に BOOT_COMPLETED で Service が再開する |
| device_probe が再起動する | 通知バーに「耐久テスト実行中」が再表示される |
| ログに新しいエントリが書き込まれる | `endurance_log.jsonl` にギャップの後、記録が再開する |

**注意：** Android 7.0 + EMUI では充電器接続での自動起動が機種設定に依存する。手動で電源を入れる必要がある場合は、それを前提として設計する（太陽光パネル＋バッテリーでの運用時、停電復帰で自動起動しない可能性がある）。

### Step 7: 筐体内温度テスト（室内）

**目的：** 想定筐体（防水ボックス等）に端末を入れた状態で、室温環境での内部温度を確認する。

**事前準備：**

- 想定する防水ボックスに端末を入れる
- USB ケーブルを通す穴を確保する
- 室温を記録する（エアコンあり/なし）

**手順：**

1. 筐体に端末を入れ、充電器を接続する
2. device_probe を起動し、**[Endurance 72h]** を押す
3. 24 時間放置する
4. ログから `cpu_temp_c` を取り出す

| 確認項目 | 合格基準 | No-Go 基準 |
|---|---|---|
| バッテリー最高温度 | ≤ 40°C（室温 25°C 前提） | > 45°C で筐体の再設計 |
| 温度の安定性 | 起動 2 時間後に平衡に達する | 単調増加し続ける場合は放熱不足 |

**注意：** `battery_temp_c` はバッテリー温度であり、CPU 温度や筐体内空気温度とは一致しない（CPU 温度はSELinuxにより取得不可）。別途、外付け温度センサーで空気温度も計測すると精度が上がる。

## Go / No-Go 判定チェックリスト

全 Step の完了後、以下を確認して Phase 0 の Go 判定を行う。

| # | 条件 | 結果 | Go/No-Go |
|---|---|---|---|
| 1 | AE ロック可 | **Go（確認済み）** | |
| 2 | プレビュー ≥ 1280×720 | **Go（確認済み：背面 2592×1944）** | |
| 3 | HW Level ≠ LEGACY | **Go（確認済み：LIMITED）** | |
| 4 | カメラ切替 ≤ 2000 ms | **Go（869 ms）** | |
| 5 | 背景差分 ≤ 50 ms | **Go（14 ms）** | |
| 6 | TFLite 推論 ≤ 200 ms | **Go（2 ms, ダミーモデル, TFLite 2.4.0, XNNPACK無効）** | |
| 7 | 72h 常駐成功 | Step 5 の結果を記入 | |
| 8 | 電源断復帰 | Step 6 の結果を記入 | |
| 9 | 筐体内温度 ≤ 40°C（室温下） | Step 7 の結果を記入 | |

**全て Go なら Phase 1（単機・既知条件の距離別試験）に進む。**

No-Go が出た場合の対応は SPEC.md §3.1 を参照。
